# Acquisition Architecture

## Purpose

The acquisition layer retrieves authorized public or licensed data through the least complex method that can reliably obtain it. It supports APIs, static HTTP, feeds, browser-rendered pages, permitted downloads, analyst-assisted sessions, and manual imports without mixing transport concerns with normalization or opportunity logic.

## Acquisition methods

### 1. Official API

Preferred when available.

Use for:

- structured data;
- stable pagination;
- explicit authentication;
- documented quotas;
- incremental cursors;
- webhooks or change streams.

Advantages:

- deterministic;
- easiest to test;
- lower resource use;
- clearer legal and contractual scope;
- better incremental updates.

### 2. Feed or bulk export

Use for RSS, Atom, JSON, CSV, STIX, TAXII, XML, or approved archive exports.

Controls:

- content-length limits;
- compression-ratio limits;
- schema validation;
- checksum and signature validation when available;
- incremental file manifests;
- immutable source-record keys.

### 3. Static HTTP collection

Use when the required data exists in ordinary HTML or a public document and does not require browser execution.

The collector may retrieve:

- HTML;
- JSON embedded in the page;
- linked public metadata;
- permitted public documents;
- response headers;
- cache validators such as ETag and Last-Modified.

Static HTTP is preferred over Chromium when it produces equivalent evidence because it is faster, cheaper, easier to replay, and has a smaller attack surface.

### 4. Browser-rendered collection

Use an isolated Chromium runtime through Playwright when one or more conditions apply:

- the page content is generated by JavaScript;
- navigation state or user interaction is required;
- an authorized authenticated session is necessary;
- downloads are initiated by a user gesture;
- a page exposes data only after rendering;
- the site requires browser-compatible cookies or client-side tokens;
- screenshots or rendered evidence are required.

Browser collection is not a universal fallback. It must be explicitly enabled in the source manifest.

### 5. Analyst-assisted browser session

Use when a legitimate workflow requires a human step, for example:

- multifactor authentication;
- accepting an updated contract;
- resolving an account-security prompt;
- reviewing a CAPTCHA or anti-automation challenge;
- choosing an export configuration;
- confirming that a download is within the approved scope.

The automation pauses and emits a `manual_action_required` task. It does not attempt to bypass the challenge.

### 6. Manual import

Use for approved exports obtained by the user or a licensed provider.

Imports pass through the same quarantine, validation, provenance, normalization, and retention controls as automated downloads.

## Selection policy

Each source declares an ordered acquisition policy:

```yaml
acquisition:
  preferred: api
  fallbacks:
    - feed
    - static_http
    - browser
  browser_allowed: true
  analyst_assistance_allowed: true
  downloads_allowed: false
```

The orchestrator never silently switches to a more intrusive or contractually different method. A fallback must already be authorized in the source manifest.

## Why HTTP and Chromium both exist

Using only HTTP would fail on JavaScript-heavy sites, user-driven exports, authenticated applications, and pages whose evidence depends on rendering.

Using Chromium for everything would create unnecessary risks:

- larger attack surface;
- higher CPU and memory consumption;
- browser crashes and leaked processes;
- session and cookie exposure;
- accidental downloads;
- non-deterministic rendering;
- more fragile selectors;
- greater difficulty replaying failures;
- higher probability of triggering anti-automation controls.

The correct architecture uses HTTP by default and Chromium only when the source contract and technical need justify it.

## Threat model

The acquisition layer treats every external source as untrusted.

Threats include:

- malicious HTML and JavaScript;
- browser exploits;
- redirect chains;
- SSRF and DNS rebinding;
- hostile files and parser exploits;
- archive and decompression bombs;
- oversized pages or endless streams;
- malformed encodings;
- tracking and fingerprinting;
- session theft;
- cross-source cookie leakage;
- malicious service workers;
- infinite navigation loops;
- source schema drift;
- partial or misleading data;
- rate-limit and account lockout;
- anti-automation challenges;
- accidental collection outside the approved scope.

## Network isolation

Collectors and browser workers run outside the API process.

Required controls:

- dedicated worker containers or sandboxes;
- no access to cloud instance metadata;
- no access to internal RFC1918 networks unless explicitly required for an owned source;
- outbound host allowlists per source;
- DNS resolution validation before and after connection;
- blocked loopback, link-local, private, multicast, and reserved ranges;
- redirect validation at every hop;
- maximum redirect count;
- TLS validation;
- source-specific proxy configuration only when contractually required;
- no arbitrary URL fetch from end-user input.

## Chromium runtime

### Isolation

Every browser job receives a fresh browser context and normally a fresh process.

The runtime uses:

- ephemeral profile directories;
- Chromium sandbox enabled;
- site isolation enabled;
- no shared cookies between sources;
- no browser extension loading;
- no access to analyst desktop files;
- restricted filesystem mount;
- restricted process capabilities;
- memory, CPU, wall-time, page-count, and navigation budgets;
- automatic process-tree cleanup.

Chromium's sandbox and site-isolation mechanisms are defense-in-depth controls, not permission to process arbitrary content without further isolation.

### Browser-context policy

```text
one source + one account + one authorization scope
= one isolated browser context
```

Contexts must not be reused across unrelated organizations or source identities.

### Request interception

The browser adapter controls requests before they leave the worker.

It may block:

- hosts outside the source allowlist;
- analytics and advertising domains when not required;
- large media resources;
- unsupported schemes;
- WebRTC;
- browser-to-localhost requests;
- file URLs;
- unauthorized third-party identity providers;
- unexpected download hosts.

Blocking third-party requests must not break the evidence required by the approved workflow. Source-specific exceptions are documented.

### Navigation budgets

A browser job declares:

- maximum pages;
- maximum navigation depth;
- maximum elapsed time;
- maximum DOM size;
- maximum response size;
- maximum screenshots;
- maximum downloads;
- maximum retry count;
- allowed host transitions.

## Authentication architecture

### Supported authentication

- API keys;
- OAuth 2.0;
- service accounts explicitly permitted by the provider;
- user-owned accounts with documented authorization;
- analyst-assisted multifactor authentication;
- short-lived session tokens issued through approved flows.

### Secret storage

Credentials are stored only in a secret manager. Database records contain a secret reference, not the secret.

Controls:

- per-source secret scope;
- per-environment separation;
- rotation dates;
- least-privilege permissions;
- access audit;
- no credentials in screenshots, traces, fixtures, logs, URLs, or Git;
- automatic redaction of authorization headers and cookies.

### Account provisioning

The system may provision a provider-approved service or test account when the provider's terms and authorization permit it.

It must not:

- create deceptive identities;
- use disposable-email accounts to avoid provider controls;
- cycle accounts after rate limits or bans;
- automate account creation contrary to platform rules;
- acquire credentials from third parties;
- share one person's session without authorization.

Account creation that requires a human remains an analyst task. Verification emails or MFA are completed through the user's authorized mailbox and account, not through evasion services.

## CAPTCHA and anti-automation handling

A challenge is a control signal, not a defect to defeat.

When detected, the collector must:

1. stop automated navigation;
2. save permitted diagnostic metadata;
3. mark the job `manual_action_required`, `access_changed`, or `policy_review_required`;
4. avoid repeated retries that could lock the account or overload the provider;
5. notify Source Operations;
6. require an analyst or provider-approved integration path.

The platform will test that CAPTCHA detection causes a safe pause. It will not include CAPTCHA-solving services, stealth plugins, fingerprint spoofing, rotating fake accounts, or other mechanisms intended to bypass access controls.

## robots.txt and crawl directives

The source review records whether robots.txt, meta robots, and X-Robots-Tag directives apply to the approved collection mode.

The manifest contains:

```yaml
crawl_policy:
  robots_reviewed_at: 2026-08-03
  robots_mode: respect
  approved_exception_reference: null
```

A documented provider authorization may define a different scope. The crawler never assumes that a public page automatically authorizes unlimited automated collection.

## Download architecture

Downloads never enter the normal application filesystem directly.

```text
HTTP or browser download event
-> download intake
-> temporary quarantine object
-> metadata and hash
-> size and type validation
-> malware and archive screening
-> permitted parser sandbox
-> redacted extraction
-> evidence artifact or rejection
-> retention and deletion workflow
```

### Download intake record

```text
download_id
source_id
job_id
request_url
final_url
initiated_at
completed_at
reported_filename
stored_object_key
size_bytes
sha256
reported_content_type
detected_content_type
classification
scan_status
parser_status
retention_until
```

### File controls

- allowlist required file types;
- random internal filenames;
- files stored outside the webroot in isolated object storage;
- content type detected independently of the header and extension;
- maximum compressed and uncompressed sizes;
- maximum archive depth and file count;
- path traversal protection;
- macros and active content treated as hostile;
- no automatic execution;
- no automatic opening on an analyst workstation;
- antivirus or malware scanning where available;
- Content Disarm and Reconstruction for approved document types when justified;
- parsing in disposable sandbox workers;
- parser time, memory, and output limits;
- raw artifact storage only when source policy permits it.

OWASP recommends defense in depth for untrusted files, including allowlisted extensions, independent type validation, generated filenames, size limits, storage outside the webroot, malware scanning, and sandboxing. The project adopts those principles.

### Parser isolation

Each parser family runs separately:

- HTML;
- PDF;
- Office Open XML;
- CSV and tabular;
- JSON and XML;
- email export;
- archive container;
- image and OCR;
- plain text.

A parser produces a typed `ParsedArtifact`, never direct database writes.

## Acquisition job state machine

```text
created
-> policy_check
-> scheduled
-> running
-> waiting_for_rate_limit
-> waiting_for_human
-> downloaded
-> parsing
-> completed

terminal alternatives:
policy_denied
access_changed
schema_changed
quarantined
failed_retryable
failed_permanent
cancelled
expired
```

Every transition is auditable and idempotent.

## Incremental updates

Collectors use the strongest available mechanism:

1. webhook or event stream;
2. provider cursor;
3. updated-since timestamp;
4. ETag or If-Modified-Since;
5. page or record checkpoint;
6. content hash and structural diff;
7. periodic full reconciliation.

A source adapter records:

- high-water mark;
- provider cursor;
- last complete collection;
- last attempted collection;
- last source record key;
- observed schema version;
- backfill position;
- reconciliation status.

## Change detection

For HTML and browser sources, distinguish:

- navigation or template changes;
- relevant data changes;
- cosmetic changes;
- disappearing records;
- changed identifiers;
- source access changes.

The adapter uses stable extracted fields and content hashes rather than comparing complete rendered pages whenever possible.

## Deletion and tombstones

When a source removes a record, the collector does not immediately erase historical evidence.

It creates a tombstone observation containing:

- source record key;
- disappearance timestamp;
- last known hash;
- reason when available;
- retention policy;
- whether dependent conclusions must expire or be recalculated.

Personal-data deletion and suppression rules take precedence over historical retention.

## Observability

Per source and acquisition mode, record:

- requests and browser navigations;
- success rate;
- latency;
- bytes transferred;
- downloads;
- records extracted;
- duplicates;
- schema failures;
- challenge detections;
- rate-limit waits;
- authentication failures;
- freshness lag;
- retry counts;
- worker crashes;
- parser quarantine rate.

Logs contain identifiers and redacted metadata, not unrestricted payloads or secrets.
