# Development Standards

## Status and purpose

This document is normative. A pull request is not complete when its feature appears to work; it is complete only when architecture, behavior, data governance, recovery, documentation, and validation agree on the same implementation.

The platform remains a modular monolith until measured operational needs justify another deployment boundary. Splitting a service is an operational decision, not a workaround for poor module design.

## Non-negotiable principles

1. One business concept has one authoritative definition.
2. Dependencies point inward toward domain rules.
3. External data is untrusted until policy, transport, schema, and mapping checks pass.
4. Collection, checkpoint advancement, and commercial projection are transactionally consistent.
5. Every generated conclusion is linked to evidence and an observed time.
6. Unit tests are deterministic and cannot use the live network.
7. Failures are typed, classified, observable, and never silently converted into success.
8. Documentation and executable configuration are versioned with the code they describe.
9. A phase is complete only after one final SHA passes every required gate.

## Single source of truth

Do not define the same rule in several files.

The following each require one authoritative owner:

- package and API version;
- source identity and authorization policy;
- collection cadence and retry policy;
- data-retention policy;
- signal taxonomy;
- opportunity-scoring rule and version;
- state-transition policy;
- field normalization rule;
- public API schema;
- roadmap lot status.

Other layers may import, project, or display an authoritative definition, but may not copy it. A duplicated constant, keyword list, score formula, state machine, or source ID is a defect unless it is a deliberate immutable protocol value documented by an ADR.

## Module ownership

Every module must declare one recognizable business responsibility and own:

- its domain language;
- entities and value objects;
- application commands and queries;
- ports used to reach external systems;
- persistence implementation for its own records;
- public contracts;
- tests at its boundary.

Provider payloads remain inside adapter packages. SQLAlchemy records remain inside infrastructure packages. HTTP request/response details remain at API or connector boundaries.

## Quantitative code budgets

Targets guide normal development. Hard limits are enforced by architecture tests.

| Element | Target | Review threshold | Hard limit |
| --- | ---: | ---: | ---: |
| Python function or method | 40 lines | 70 lines | 120 lines |
| Python class | 200 lines | 250 lines | 300 lines |
| Handwritten Python source file | 250 lines | 300 lines | 400 lines |
| Required function parameters | 5 | 8 | 10 total parameters |
| Control-flow nesting | 3 levels | 4 levels | 6 levels |
| React component | 150 lines | 200 lines | 300 lines |
| Handwritten test file | 350 lines | 500 lines | 650 lines |

Generated files, database migrations generated by a tool, and static fixtures must be stored in dedicated locations. They are exempt only from size limits, not from review, provenance, or safety requirements.

Crossing a review threshold requires refactoring or an ADR explaining why splitting would reduce correctness or clarity. Hard limits cannot be bypassed by an inline ignore.

## Function and class rules

A function performs one operation at one abstraction level. Split it when it mixes two or more of:

- transport;
- authorization or source policy;
- parsing;
- normalization;
- entity resolution;
- persistence;
- scoring;
- notification;
- presentation.

Avoid boolean parameters that switch between different workflows. Prefer separate commands, strategies, or policy objects.

A class has one reason to change. Do not create generic `Manager`, `Helper`, `Utils`, `Common`, or `Service` containers. Names must state the capability they own.

Prefer immutable value objects, explicit request objects, pure policies, and injected clocks or identifier generators. Global mutable state is forbidden.

## Definition and naming integrity

- A module or class scope may not redefine a function or class name.
- Wildcard imports are forbidden.
- Public names use the canonical domain vocabulary.
- Temporary compatibility facades may re-export names but may not contain competing implementations.
- Deprecated definitions require an owner, replacement, removal issue, and deadline.

Canonical distinctions:

- `observation`: source material that was collected;
- `claim`: an assertion made by a source;
- `evidence`: retained support with provenance;
- `signal`: normalized information relevant to a need;
- `need`: a versioned hypothesis;
- `opportunity`: a human-reviewed commercial object;
- `alert`: a notification about meaningful change.

## Backend dependency direction

```text
API / CLI / worker composition
        -> application commands and queries
        -> domain policies and entities

infrastructure implements application ports
external adapters produce approved observations and projections
```

Forbidden dependencies include:

- domain to FastAPI, SQLAlchemy, HTTP clients, Alembic, Redis, OpenSearch, or browser libraries;
- domain to `infrastructure`, `api`, or provider adapter packages;
- one module to another module's infrastructure implementation;
- external adapters to organization, evidence, or opportunity persistence implementations;
- opportunity rules to provider-specific schemas;
- API routes implementing scoring, retry, parsing, or entity-resolution logic.

Architecture tests enforce the domain and adapter boundaries. Any new boundary must be encoded in tests in the same pull request that introduces it.

## API and application rules

An API route may validate transport input, enforce endpoint authorization, construct one command or query, call one handler, and translate the result. It may not perform business SQL, parse provider data, score opportunities, or implement retries.

Each application handler must have:

- typed input and result;
- an explicit authorization or policy decision;
- a visible transaction boundary;
- deterministic behavior for the same inputs;
- idempotency when called by a queue or external callback;
- typed errors;
- tests for success, rejection, conflict, and dependency failure.

## Domain rules

Domain code owns invariants, state transitions, confidence, freshness, scoring, and explanations. It must be deterministic unless time, identifiers, or a model are passed through explicit interfaces.

A score must expose:

- rule and version;
- input evidence IDs;
- component values;
- penalties and confidence;
- calculation timestamp;
- reproducible configuration or hash;
- human-readable explanation.

## Persistence and transaction rules

- A repository belongs to one module.
- Repository interfaces use domain or application types.
- SQLAlchemy records never escape infrastructure code.
- Cross-module reporting uses read models or query services.
- Writes that represent one business outcome commit or roll back together.
- A checkpoint never advances when observation or projection persistence fails.
- Replays use deterministic idempotency keys.
- Mutable projections update approved fields without replacing immutable identity or history.
- Concurrency behavior is tested against PostgreSQL when locking or conflict handling matters.

Database changes require a reversible migration, representative-data test, and startup validation after `upgrade -> downgrade -> upgrade`.

## Time, identity, and provenance

- Runtime timestamps are timezone-aware UTC.
- Source time, published time, observed time, and collected time remain distinct.
- Deterministic identifiers are used when source identity is stable.
- Random identifiers are reserved for genuinely new events or commands.
- Every observation stores source ID, source record key, adapter version, collection job, hash, timestamps, classification, retention, and source URL where permitted.
- Raw content is retained only when the source policy explicitly permits it.

## External connector rules

Every connector package separates:

1. transport client;
2. response-size, host, path, redirect, and content-type controls;
3. provider schema;
4. pagination or checkpoint collection;
5. mapping and deterministic identity;
6. orchestration error classification;
7. fixtures and tests.

Before the first network request, the connector must validate the source registry, authorization, purpose, host, path, automation permission, raw-storage permission, and quota.

A connector must not calculate final opportunity scores, write directly to canonical persistence, bypass policy, follow an unauthorized redirect, or silently accept schema drift.

CAPTCHA, MFA, changed terms, bot challenges, or account-security prompts cause a safe pause and human task. Circumvention is out of scope.

## Error and recovery rules

Errors are translated at boundaries into stable categories:

- validation;
- authorization;
- policy denied;
- not found;
- conflict or stale version;
- rate limited;
- dependency unavailable;
- unsafe response;
- source schema changed;
- retryable collection failure;
- permanent collection failure;
- lost lease;
- dead letter.

Retries are bounded and classified. Unknown exceptions are observable and must not hide the original cause. No broad exception assertion or catch may make an unrelated defect look expected.

## Logging and data handling

Logs and exceptions must not contain secrets, cookies, tokens, credentials, unrestricted payloads, victim files, candidate data, private communications, or full professional-contact exports.

Public repositories contain only synthetic, minimized, provider-published, or explicitly redistributable fixtures. Real collected datasets and production exports remain outside Git.

## Frontend rules

A frontend feature owns route composition, API hooks, feature state, presentation components, forms, and tests. Shared components must be genuinely reusable.

Separate server data, orchestration state, URL state, and presentation. Do not copy server records into an unrelated global store.

Every conclusion shown to an analyst must make source, evidence, timestamps, confidence, freshness, claim type, and review status accessible. Inference must never be presented as confirmed fact.

## Required test suites

Every feature selects all applicable suites; a happy-path unit test is never sufficient.

| Change | Mandatory suites |
| --- | --- |
| Domain policy or score | unit, boundaries, negative cases, explanation, regression |
| Parser or mapper | schema, fixture, mapping, malformed input, deterministic identity |
| External connector | policy-before-network, transport, response limits, HTTP classification, checkpoint, removal/change behavior |
| Persistent write | integration, idempotency, rollback, conflict/concurrency where applicable |
| Database schema | migration cycle, representative data, constraints, downgrade |
| API contract | success, validation, authorization, error mapping, redaction |
| UI workflow | loading, empty, partial, stale, error, success, action result |
| Scheduler or worker | lease, retry, circuit, interruption, late completion, dead letter |
| Compliance control | allow, deny, retention, suppression/deletion propagation, audit evidence |

Unit tests are fast, deterministic, and network-free. `tests/unit/conftest.py` blocks socket connections. HTTP behavior uses fake clients or `httpx.MockTransport`. Routine CI never depends on a live third-party service.

## Coverage policy

- Backend line and branch coverage: at least 90% globally.
- New deterministic connector and orchestration code: target 95%.
- Policy, scoring, state transitions, redaction, suppression, and retention: target 95% or higher.
- Coverage exclusions require a documented reason and may not hide a business branch.
- Coverage does not replace assertions about invariants, rollback, evidence, or side effects.

## CI gate order

A pull request must pass on one final SHA:

1. dependency installation and consistency;
2. dependency audit;
3. Ruff;
4. Mypy strict;
5. architecture and release-contract tests;
6. reversible PostgreSQL migrations;
7. complete backend tests with line and branch coverage;
8. frontend dependency audit;
9. TypeScript checking;
10. production frontend build;
11. documentation and roadmap consistency;
12. review threads resolved.

A later documentation or metadata commit invalidates earlier validation. The final report records the exact tested SHA, run, test count, coverage, migration result, frontend result, and known limitations.

## Pull-request discipline

Each pull request has one coherent objective and states:

- problem and non-goals;
- architecture and owned modules;
- source/data/legal impact;
- failure and recovery behavior;
- migration and rollback plan;
- tests added by category;
- documentation changed;
- exact validation results.

No permanent skip, broad ignore, architecture allowlist, or quarantined test is accepted without an owner, issue, reason, and expiry date.

## Roadmap and phase completion

`docs/PROJECT_DELIVERY_PLAN.md` is the authoritative lot plan. Lot numbers are continuous. Every lot declares status, objective, dependencies, deliverables, test suites, non-goals, and exit gate.

Allowed statuses:

- `IMPLEMENTED_VALIDATED`;
- `IN_PROGRESS`;
- `PLANNED_LOCKED`;
- `BLOCKED`;
- `DEFERRED`.

Only a final green SHA may move a lot to `IMPLEMENTED_VALIDATED`. A roadmap validator checks continuity and mandatory fields.

## Architecture decision records

Create an ADR for decisions that affect several modules or are expensive to reverse, including database or queue selection, service extraction, event guarantees, entity resolution, scoring versioning, browser isolation, professional-contact data isolation, multi-tenancy, search indexing, or CRM ownership.
