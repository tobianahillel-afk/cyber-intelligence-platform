# Development Standards

## Purpose

These rules preserve modularity as the platform grows. They apply to backend, frontend, workers, source adapters, schemas, migrations, and tests.

## Default architectural style

Use a modular monolith until a demonstrated scaling, isolation, or deployment requirement justifies extracting a service.

A module must have:

- one clearly stated business responsibility;
- owned domain concepts;
- an application interface;
- owned persistence abstractions;
- explicit events or contracts;
- tests at its boundary;
- no knowledge of provider-specific payloads outside adapters.

## Source-code size budgets

### Python and TypeScript

- Function target: at most 40 logical lines.
- Function review threshold: 70 logical lines.
- Class target: at most 250 lines.
- Class review threshold: 400 lines.
- Source file target: at most 300 lines.
- Source file review threshold: 500 lines.
- Route file target: at most 250 lines.
- React component target: at most 200 lines.
- Test file target: at most 500 lines.

Generated files, migrations generated by tools, and static fixtures are exempt but must be stored separately from handwritten application code.

Exceeding a review threshold requires either refactoring or an Architecture Decision Record explaining why splitting would reduce clarity.

## Function rules

A function should do one recognizable job.

Split a function when it mixes two or more of:

- transport;
- authentication;
- policy checks;
- parsing;
- normalization;
- persistence;
- scoring;
- notification;
- presentation formatting.

Avoid boolean parameters that radically change behavior. Prefer separate commands, strategies, or policy objects.

Avoid functions with more than five required parameters. Introduce a typed request object or value object when the parameters represent one concept.

## Class rules

A class must have one reason to change.

Do not create `Manager`, `Helper`, `Utils`, `Common`, or `Service` classes containing unrelated operations. Names must describe the business capability, for example:

- `OpportunityScorer`
- `ContractRenewalEstimator`
- `OrganizationResolver`
- `SourcePolicyEvaluator`
- `EvidenceRedactor`

Prefer immutable value objects and pure domain policies where possible.

## Backend dependency direction

```text
api -> application -> domain
infrastructure -> application ports
adapters -> shared contracts
```

Forbidden dependencies:

- domain to FastAPI;
- domain to SQLAlchemy;
- domain to HTTP clients;
- domain to Redis, OpenSearch, or browser libraries;
- API routes directly to database sessions for business operations;
- one module to another module's infrastructure;
- opportunity rules to source-specific payloads;
- source adapters directly to domain repositories.

## Backend route rules

A route may:

- validate HTTP input;
- enforce endpoint authorization;
- construct a command or query;
- call one application handler;
- map the result to an HTTP response.

A route may not:

- calculate opportunity scores;
- perform entity resolution;
- parse provider payloads;
- run SQL business queries directly;
- send notifications;
- implement retry logic.

## Application-handler rules

Command handlers change state. Query handlers read state.

Each handler must:

- have a typed input;
- have a typed result;
- perform authorization or policy decisions through declared ports;
- define its transaction boundary;
- emit domain events only after successful state changes;
- be idempotent when invoked by queues or external callbacks.

## Domain rules

Domain code contains:

- entities;
- value objects;
- domain events;
- invariants;
- scoring policies;
- state-transition policies;
- confidence and freshness calculations.

Domain code must be deterministic except when a clock, identifier generator, or model is passed through an explicit interface.

## Repository rules

- A repository belongs to one module.
- Repository interfaces use domain or application types.
- SQLAlchemy models remain infrastructure details.
- Cross-module reporting uses read models or query services.
- Avoid a generic repository abstraction that hides necessary query behavior.

## Event rules

Events use past-tense business names:

- `OpportunityCreated`
- `OpportunityScoreChanged`
- `EvidenceAccepted`
- `ContactSuppressed`
- `SourcePaused`

Events must include:

- event ID;
- event version;
- occurred-at timestamp;
- actor or process identity when relevant;
- aggregate identifier;
- correlation and causation identifiers.

Do not place complete source payloads, credentials, secrets, or unrestricted personal data in events.

## Source-adapter rules

Every source adapter has an isolated directory and manifest.

The adapter must separate:

1. transport client;
2. pagination and collection;
3. provider-schema validation;
4. mapping to a raw observation envelope;
5. fixture and contract tests.

The adapter must not:

- resolve organizations;
- identify final decision makers;
- calculate opportunity scores;
- write directly to canonical domain tables;
- reuse another provider's private schema;
- bypass the source registry.

## Browser-worker rules

Browser automation belongs to a dedicated adapter and worker runtime.

Each browser job must have:

- source policy ID;
- target host and approved paths;
- research purpose;
- permitted data categories;
- time and page budget;
- download policy;
- authentication mode;
- retention classification;
- requester and audit context.

The browser runtime must expose a narrow interface such as:

```python
class BrowserResearchPort(Protocol):
    async def execute(self, request: BrowserResearchRequest) -> BrowserResearchResult:
        ...
```

Browser implementation details must not leak into the research or opportunity modules.

## Frontend feature rules

Each frontend feature owns:

- route-level composition;
- API hooks;
- feature components;
- local forms;
- feature-specific tests.

Shared components must be genuinely reusable. Do not move a component to `shared` merely to avoid a relative import.

Separate:

- data fetching;
- state and orchestration;
- presentation;
- reusable primitives.

A large React screen should normally be split into:

```text
Page
-> feature container
-> domain sections
-> small presentation components
-> drawers and dialogs
```

## Frontend state rules

- Server state stays in the query cache.
- URL state stores shareable filters, sorting, pagination, date range, and selected tab.
- Local state stores temporary UI interaction.
- Global client state is reserved for application-wide concerns such as session, theme, and active workspace.
- Do not duplicate server records into a global store.

## UI data rules

Every displayed observation or conclusion must expose, directly or through a details panel:

- source;
- observed or published timestamp;
- collected timestamp;
- confidence;
- freshness state;
- claim or observation type;
- analyst review status.

The UI must not label an inferred technology-vulnerability relation as a confirmed vulnerability.

## Naming rules

Use domain language consistently.

Preferred distinctions:

- `observation`: something collected from a source;
- `claim`: a source's assertion;
- `evidence`: retained support for an observation or claim;
- `signal`: a canonical fact or inference relevant to detection;
- `need`: a hypothesized cybersecurity requirement;
- `opportunity`: a commercial object reviewed by a human;
- `alert`: a user notification about a meaningful change.

Do not use these terms interchangeably.

## Error handling

Use typed application errors. Translate them at boundaries.

Categories:

- validation;
- authorization;
- policy denied;
- not found;
- conflict or stale version;
- rate limited;
- dependency unavailable;
- source schema changed;
- retryable collection failure;
- non-retryable collection failure.

Never silently ignore a source parsing error. Preserve a redacted failure record and route it to source operations.

## Testing pyramid

### Unit tests

- domain policies;
- score components;
- freshness decay;
- state transitions;
- parser logic;
- mapping logic.

### Contract tests

- source fixtures;
- API schemas;
- event schemas;
- generated frontend client compatibility.

### Integration tests

- PostgreSQL repositories;
- Redis jobs and locks;
- OpenSearch indexing;
- object storage;
- provider sandboxes or recorded permitted fixtures.

### End-to-end tests

- signal to opportunity;
- opportunity triage;
- organization workspace;
- research job and evidence review;
- source pause and recovery;
- suppression and deletion propagation.

## Architecture tests

Automated tests must eventually verify:

- module dependency direction;
- no domain imports of frameworks;
- no cross-module infrastructure imports;
- API routes do not import SQLAlchemy repositories directly;
- adapters do not import opportunity repositories;
- frontend features do not import another feature's internal components.

## Pull-request checklist

A change is ready when:

- module ownership is clear;
- no review threshold is exceeded without explanation;
- source and personal-data impacts are documented;
- logs contain no secrets or unrestricted source payloads;
- failure and retry behavior is tested;
- migrations are reversible or have a documented rollback plan;
- API and event changes are versioned;
- UI states cover loading, empty, partial, stale, success, and failure;
- documentation is updated.

## Decision records

Create an ADR for decisions that affect several modules or are expensive to reverse, including:

- database or queue selection;
- modular monolith versus service extraction;
- event delivery guarantees;
- entity-resolution strategy;
- scoring versioning;
- browser isolation model;
- multi-tenancy;
- professional-contact data isolation;
- search-index design.
